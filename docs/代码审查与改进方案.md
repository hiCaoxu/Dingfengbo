## 1. 项目总评

**架构健康度：7 / 10**

整体是一个完成度相当高的单机优先应用：分层意识明确（db / services / ui）、同步协议已是「服务端单调序列 + 幂等确认」的正确形态、打包链路完整。扣分主要在：SQLite 并发原语缺失（P0）、服务端序列分配存在并发竞态（P0）、冲突解决完全裸奔在客户端时钟上（P1）、全项目零日志（P3）。

### 最值得肯定的 3 个设计决策

1. **同步游标采用服务端单调 `sync_seq` 而非客户端时间戳**（`app/services/sync.py:59-79` + `server/main.py:79-101`）。pull 的增量边界由服务端序列决定，天然免疫客户端时钟回拨/时区差异——这是整个同步系统最正确的一块。
2. **`mark_clean` 按「上传时的 `updated_at` 版本」精确确认**（`app/db/repo.py:70-96`）。推送期间用户继续编辑同一条记录时不会被误标 clean，避免了「新编辑被静默吞掉」的经典并发坑，且重复推送天然幂等（LWW 等值 + `_same_version` 比对，`repo.py:119-130`）。
3. **数据目录与安装目录分离 + 写入探测回退**（`app/config.py:13-30`）。`DINGFENGBO_DATA_DIR` 可覆盖、不可写时回退用户主目录，MSI 卸载不触碰用户数据，是桌面端数据安全的正确姿势。

### 最危险的 3 个隐患

1. **客户端与服务端的 SQLite 引擎都没有 WAL 模式和 busy_timeout**（`app/db/session.py:16-18`、`server/main.py:22`）。UI 线程写库与同步线程 `apply_remote` 并发时直接抛 `database is locked`，用户的一次保存可能整体失败回滚；服务端两个设备同时 push 时互相 500。
2. **服务端 `sync_seq` 用 `SELECT MAX(...) + 1` 非原子分配**（`server/main.py:122-126`）。两个客户端并发 push 同一张表时会分配到相同序列号，后续 pull 的 `sync_seq > cursor` 条件将**永久跳过其中一条记录**——这是静默数据丢失级缺陷。
3. **「最后写入获胜」完全依赖各端本地时钟，且客户端从不校验时钟偏移**（`app/db/repo.py:159`、`app/services/sync.py:113`）。服务端每次都回传 `server_time`，但客户端收到后从未使用。一台时钟快 5 分钟的设备会在冲突中永远获胜，另一台设备的更新被静默丢弃，无任何提示。

## 3. 关键问题深度分析

### 深度分析 1（P0）：SQLite 无 WAL / busy_timeout —— 并发写入直接报错

**根因分析**

两端引擎都是最朴素的 `create_engine`：

```python
# app/db/session.py:16-18（客户端）
engine = create_engine(
    f"sqlite:///{DB_PATH}", connect_args={"check_same_thread": False}, future=True
)
# server/main.py:22（服务端）
engine = create_engine(f"sqlite:///{DB_PATH}", connect_args={"check_same_thread": False}, future=True)
```

SQLite 默认 rollback journal + 整个数据库级写锁。本应用恰恰有两个长期并发的写来源：

- 客户端：UI 线程（`forms.py` 9 处 save、`todo.py` toggle）与同步线程（`scheduler.py` 的 `threading.Timer` → `sync_once` → `apply_remote`/`mark_clean`）并发写同一个 db 文件；
- 服务端：uvicorn 把 `def` 端点放进 anyio 线程池（默认 40 线程），两台设备的 push 天然并发。

写锁相遇时，busy_timeout 未显式设置（pysqlite 默认 5s，但 SQLAlchemy 池化重连后行为不可控），瞬时冲突即抛 `OperationalError: database is locked`。客户端 `session_scope` 会 rollback 并上抛——用户在表单里点「保存」直接失败；服务端则返回 500，客户端把整批 push 判为「离线」延后重试，表现为同步偶发性卡住。

**Before / After**

```python
# Before（app/db/session.py:16-18）
engine = create_engine(
    f"sqlite:///{DB_PATH}", connect_args={"check_same_thread": False}, future=True
)

# After
from sqlalchemy import event

engine = create_engine(
    f"sqlite:///{DB_PATH}",
    connect_args={"check_same_thread": False, "timeout": 15},
    future=True,
)

@event.listens_for(engine, "connect")
def _set_sqlite_pragma(dbapi_connection, _record):
    cursor = dbapi_connection.cursor()
    cursor.execute("PRAGMA journal_mode=WAL")
    cursor.execute("PRAGMA synchronous=NORMAL")
    cursor.execute("PRAGMA busy_timeout=15000")
    cursor.close()
```

`server/main.py` 的 engine 做完全相同的改造（建议把「建 engine + PRAGMA」提成 `app/db/session.py` 的公共函数 `create_sqlite_engine(path)`，两端复用）。

**为什么这样改能解决问题**

- `timeout=15` / `busy_timeout=15000` 让锁冲突从「立即报错」变为「最多等 15 秒」，覆盖同步批次这种秒级临界区；
- WAL 模式下读不阻塞写、写不阻塞读，UI 查询与同步写入可真正并行，只剩写-写互斥（且由 busy_timeout 兜底）；
- `synchronous=NORMAL` 在 WAL 下是安全的（SQLite 官方保证），写事务耗时显著下降，直接缓解 P2 的 UI 线程写库卡顿；
- 不引入任何新依赖、不改变数据目录结构（WAL 只是在 db 旁多一个 `-wal` 文件）。

### 深度分析 2（P0）：服务端 `sync_seq` 并发分配竞态 —— 永久性增量丢失

**根因分析**

```python
# server/main.py:122-126
if change.get("changed"):
    if table not in next_sequences:
        next_sequences[table] = session.scalar(select(func.max(model.sync_seq))) or 0
    next_sequences[table] += 1
    obj.sync_seq = next_sequences[table]
```

这是教科书式的读-改-写竞态：设备 A、B 同时 push 同一表，两个线程各自 `SELECT MAX` 都读到 N，各自算出 N+1，先后 commit——两条记录 `sync_seq` 同为 N+1。

致命之处在于后果不可逆：另一台已同步到游标 N+1 的设备 C 下次 pull 时条件是 `sync_seq > N+1`（`server/main.py:83`），**那条被挤掉的记录对 C 永远不可见**。没有全量对账机制，丢失静默发生。这就是「多端同时在线时无数据丢失」承诺的破口。

**Before / After**

```python
# Before（server/main.py:122-126）：应用层 MAX+1

# After 方案 A（推荐，最小改动）：单表全局序列 + 事务内原子自增
class SyncSequence(Base):
    __tablename__ = "sync_sequences"
    id: Mapped[int] = mapped_column(Integer, primary_key=True)  # 恒为 1
    value: Mapped[int] = mapped_column(Integer, default=0, nullable=False)

def next_sequences(session, n: int) -> list[int]:
    """一个事务内原子领取 n 个全局序列号。"""
    session.execute(
        text("INSERT INTO sync_sequences(id, value) VALUES(1, 0) "
             "ON CONFLICT(id) DO NOTHING")
    )
    row = session.execute(
        text("UPDATE sync_sequences SET value = value + :n RETURNING value"),
        {"n": n},
    ).one()
    hi = row.value
    return list(range(hi - n + 1, hi + 1))
```

push 里收集所有 `changed` 的记录，一次性领取序列段后按提交顺序赋值。同时 `sync_seq` 从「每表一个序列」简化为「全局一个序列」（pull 的 `> cursor` 语义不受影响，游标仍按表存）。

方案 B（不改 schema 的临时缓解）：给 push 加一个进程级 `threading.Lock` 包裹「取号 + commit」。单进程 uvicorn 下有效，但无法横向扩容，仅作热修。

**为什么这样改能解决问题**

序列分配下沉为数据库的单个 `UPDATE` 语句，SQLite 的写事务原子性保证不会有两个连接拿到同一段；`RETURNING` 一次往返完成「自增并读回」。游标的单调性重新变得可信，pull 的增量边界恢复严密。全局序列还顺带消除了「每表各自取 MAX」的 N 次查询。

### 深度分析 3（P0/P1）：LWW 裸奔在客户端时钟上 —— 时钟回拨即静默丢数据

**根因分析**

冲突裁决只有一个依据——记录上的 `updated_at`：

```python
# app/db/repo.py:159（客户端 apply_remote）
if obj.updated_at and obj.updated_at >= remote_time:
    ...continue  # 本地获胜，远端被丢弃
```

而 `updated_at` 来自各设备自己的 `datetime.utcnow()`（`app/db/models.py:17-18`）。服务端每次响应都带 `server_time`（`server/main.py:100,129,137`），但客户端 `sync.py` 从未读取它——这个字段目前是完全浪费的。

后果场景：

1. 设备 A 时钟快 10 分钟。A、B 同时编辑同一待办，B 的修改（真实时间更晚）`updated_at` 反而更小，pull 时被 B 本地的 LWW 判断丢弃——**B 的编辑无声消失**。
2. 设备时钟回拨（NTP 校时/用户手改）：回拨期间产生的 `updated_at` 比云端旧记录更小，本地新编辑在服务端 `apply_remote` 被判负，同样静默丢失。
3. `datetime.utcnow()` 在 Python 3.12+ 已 deprecated，且 naive 时间一旦某端混入 aware 时间（如未来引入时区），`>=` 比较直接抛 `TypeError`。

**Before / After**

```python
# Before（app/services/sync.py:109-115）
with httpx.Client(timeout=10.0) as client:
    self._pull(client, settings)
    self._push(client)

# After：同步中维护时钟偏移估计
class SyncClient:
    def __init__(self) -> None:
        ...
        self.clock_offset = 0.0  # 服务端 - 本地，秒

    def _observe_server_time(self, payload: dict) -> None:
        raw = payload.get("server_time")
        if not raw:
            return
        server_now = datetime.fromisoformat(raw)
        self.clock_offset = (server_now - datetime.utcnow()).total_seconds()
        if abs(self.clock_offset) > 120:
            self.status = "本机时钟异常，请校准系统时间"
```

并在写路径加盖「偏移修正后的时间戳」：

```python
# app/db/repo.py:27-29
def mark_dirty(obj: SyncMixin, clock_offset: float = 0.0) -> None:
    obj.updated_at = utcnow() + timedelta(seconds=clock_offset)
    obj.sync_status = "pending"
```

**为什么这样改能解决问题**

不追求精确对时（那需要 NTP/向量时钟的复杂度），只做「以服务端时间为公共时间轴」的偏移修正：所有端的 `updated_at` 被拉回同一坐标系，LWW 的「最后」重新等价于真实世界的「最后」。偏移超阈值时显式告警，把「静默丢数据」变成「用户可见的时钟异常提示」。改动只在客户端，协议零变更。

### 深度分析 4（P0）：Bearer token 全链路明文 —— 存储、展示、服务端主键

**根因分析**

token 在三个环节裸奔：

1. **本地明文落盘**：`save_settings` 原样写入 `settings.json`（`app/config.py:59-65`），且该文件就在数据目录，任何备份/同步盘工具都会带走它。
2. **UI 明文显示**：设置对话框用通用 `form_field`（`app/ui/forms.py:546`），未设 `password=True`，肩窥即泄露。
3. **服务端把 token 本体当 owner 主键**：`owner_of` 直接 `return token[:64]`（`server/main.py:58`），云端 `cloud.db` 里每一行数据都明文镶嵌着完整访问凭证——库文件泄露 = 所有用户数据永久失守，连「改密码」都无法补救（token 即身份）。

**Before / After**

```python
# Before（server/main.py:57-58）
def owner_of(authorization: str | None) -> str:
    ...
    return token[:64]

# After：身份与存储键分离，DB 里只存不可逆摘要
def owner_of(authorization: str | None) -> str:
    ...
    return hashlib.sha256(f"dingfengbo-v1\0{token}".encode()).hexdigest()
```

```python
# Before（app/ui/forms.py:546）
token = form_field("同步令牌", settings.get("sync_token", ""))

# After：遮蔽显示 + 粘贴板友好
token = form_field("同步令牌", settings.get("sync_token", ""))
token.password = True
token.can_reveal_password = True
```

本地存储侧（不加依赖的务实方案）：`settings.json` 中 token 改存 `base64` 混淆字段并配合文件 ACL 提示；若愿意加一个轻量依赖，Windows 上用 `win32crypt`/DPAPI 加密（PyInstaller 打包无压力）。同时给设置页加「测试连接」按钮，调用 `GET /api/sync/check` 验证 token 有效性（顺带解决问题 #6 的误报离线）。

**为什么这样改能解决问题**

服务端摘要是关键一击：owner 键不可逆后，`cloud.db` 泄露不再等于凭证泄露（攻击者拿到摘要无法反推 token、也无法伪造 Authorization 头——服务端按摘要匹配）。加 `\0` 域分隔前缀防止与其他系统的 sha256(token) 彩虹表碰撞。注意：**切换摘要方案是一次性数据迁移**（把现有 owner_id 批量 UPDATE 成摘要值），需写进 migrations 或部署手册，属于路线图「短期」项。

### 深度分析 5（P2）：笔记预览每次击键 O(全文) 重渲染

**根因分析**

调用链：`TextField.on_change`（`app/ui/notes.py:226`）→ `_update_preview`（`notes.py:230-233`）→ `parse(全文)`（`markdown.py:91`）→ 每个代码块 `highlight_lines`（`markdown.py:39`，逐 token 建 `ft.TextSpan`）→ 整棵控件树替换 + `page.update()`。

一篇 5 万字、含 10 个代码块的笔记，每次击键的代价是：正则扫描全文 + Pygments 词法分析 10 段代码 + 创建数百个 Flet 控件 + 一次完整 diff 渲染。键盘输入必然卡顿，且 `on_change` 在 UI 线程执行，阻塞期间连光标都画不出来。

**Before / After**

```python
# Before（app/ui/notes.py:226,230-233）
source = ft.TextField(..., on_change=lambda e: _update_preview())

def _update_preview() -> None:
    preview.content = render_markdown(source.value or "")
    page.update()

# After：防抖 + 大文档降级
_PREVIEW_DEBOUNCE_MS = 400
_PREVIEW_PLAINTEXT_THRESHOLD = 50_000  # 字符
_preview_timer: threading.Timer | None = None

def _on_source_change(e) -> None:
    global _preview_timer
    if _preview_timer is not None:
        _preview_timer.cancel()
    _preview_timer = threading.Timer(
        _PREVIEW_DEBOUNCE_MS / 1000, _render_preview_async
    )
    _preview_timer.daemon = True
    _preview_timer.start()

def _render_preview_async() -> None:
    text = source.value or ""
    if len(text) > _PREVIEW_PLAINTEXT_THRESHOLD:
        blocks = [{"type": "text", "text": "（文档过大，预览已降级为纯文本）"},
                  {"type": "code", "lang": "", "code": text}]
    else:
        blocks = parse(text)  # CPU 密集部分放后台线程
    def apply() -> None:
        preview.content = build_blocks(blocks)
        page.update()
    page.run_task(apply)  # 回到 UI 线程
```

（`render_markdown` 拆成纯函数的 `parse/build` 两段，与现有 `markdown.py` 结构兼容；`page.run_task` 的用法沿用 `app/ui/scheduler.py:52` 的既有模式。）

**为什么这样改能解决问题**

防抖把「每击键一次」降为「停顿 400ms 一次」，消除 90% 以上的冗余渲染；重计算移出 UI 线程后，打字不再被高亮阻塞；阈值降级保证极端大文档的最坏情况有界。Flet 控件创建仍必须在 UI 线程，因此拆分点是「`parse` 后台 / `build` 前台」——这正好也是 `markdown.py` 现有的天然分层。

### 深度分析 6（P2）：首页与记账页的全表内存聚合

**根因分析**

- `app/ui/home.py:116-127`：热力图对 7 张同步表全表 `scalars()` 取出（仅过滤 `is_deleted`），在 Python 里 `defaultdict` 按日计数。使用 N 年后每次进首页都扫全量历史。
- `home.py:261-262`：`notes = list(...)` 取出**全部笔记正文**（含大文本列）只为 `choice` 一条随机展示。
- `app/ui/finance_ui.py:58-66`：一次 `build` 内 `month_summary + account_balances + total_assets + six_month_trend` 至少扫交易表 9 次；`finance.py:101-109` 的六个月趋势逐月再查 6 次。
- `finance_ui.py:113-128`：全部交易读进内存再做年/月过滤与分页切片，分页完全没下推 SQL。

**Before / After**

```python
# Before（app/ui/home.py:116-127，示意）
for model in (Diary, Todo, Exercise, Diet, Weight, Sleep, Transaction):
    rows = session.scalars(select(model).where(model.is_deleted.is_(False)))
    for row in rows:
        counts[row.date] += 1

# After：聚合下推 SQL，且只取热力图窗口（约 1 年）
from sqlalchemy import func

def _activity_counts(session, since: date) -> dict[date, int]:
    counts: dict[date, int] = defaultdict(int)
    for model in (Diary, Todo, Exercise, Diet, Weight, Sleep, Transaction):
        stmt = (
            select(model.date, func.count())
            .where(model.is_deleted.is_(False), model.date >= since)
            .group_by(model.date)
        )
        for day, n in session.execute(stmt):
            counts[day] += n
    return counts
```

```python
# Before（home.py:261-262）
notes = list(session.scalars(select(Note).where(Note.is_deleted.is_(False))))
note = choice(notes) if notes else None

# After
note = session.scalar(
    select(Note).where(Note.is_deleted.is_(False))
    .order_by(func.random()).limit(1)
)
```

```python
# Before（finance_ui.py:124 附近）：内存过滤+切片
filtered = [tx for tx in transactions if matches(tx)]
page_items = filtered[offset:offset + page_size]

# After：过滤条件下推 WHERE，分页用 LIMIT/OFFSET，
# 总数用 SELECT COUNT(*) 单独取
```

**为什么这样改能解决问题**

SQLite 对带索引的 `GROUP BY`/`COUNT` 是毫秒级且内存恒定，与数据总量基本脱钩；`ORDER BY RANDOM() LIMIT 1` 避免把全部 `content` 大字段读进 Python。记账页的 9 次重复扫描可用一个「一次查询、内存复用」的月度聚合函数收敛为 2~3 次。这些改动全部在既有分层约定内（home 缺的正是 finance.py 那种收 session 参数的 service 函数），不需要任何新框架。

## 4. 同步机制专项审查

### 4.1 正常流程时序（文字描述）

```
启动/定时(5min)/写后(10s 防抖)/手动
        │
        ▼
sync_once()  ──非阻塞抢锁(重入直接返回当前状态)
        │
        ▼  load_settings()（token/server_url）
   ┌─ _pull ──────────────────────────────────────────────┐
   │ 读本地游标(按 sha256(server+token) 分键, settings.json)│
   │ loop: POST /api/sync/pull {cursors, limit:200}        │
   │   服务端: 逐表 WHERE owner AND sync_seq > cursor       │
   │          ORDER BY sync_seq LIMIT 201 (判 has_more)     │
   │   客户端: session_scope 内 apply_remote(本地LWW裁决)   │
   │          游标落盘 → has_more 则继续                    │
   └───────────────────────────────────────────────────────┘
        │
        ▼
   ┌─ _push ──────────────────────────────────────────────┐
   │ pending_changes(每表≤500, 序列化全字段)               │
   │ POST /api/sync/push {changes}                         │
   │   服务端: owner 覆盖 → apply_remote(服务端LWW裁决)     │
   │          changed 的记录分配 sync_seq → commit          │
   │   客户端: mark_clean(仅 updated_at 精确匹配的版本)     │
   │          purge_deleted(clean 墓碑物理删除)             │
   └───────────────────────────────────────────────────────┘
        │
        ▼
 更新 status/last_sync → page.run_task 回 UI 线程刷新状态与内容
```

### 4.2 异常场景覆盖矩阵

| 场景 | 当前行为 | 评价 |
|------|---------|------|
| 断网/超时 | httpx 异常 → 「离线可用」，本地数据不受影响，下周期重试 | ✅ 合格 |
| push 成功后响应丢失（重复推送） | 重推同版本，服务端 LWW 等值 + `_same_version` 判 `changed=False`，accepted 原样返回，客户端正常 mark_clean | ✅ 幂等设计正确 |
| push 中途崩溃（部分写库） | 服务端整个 push 在**一个 session/事务**内，崩溃即整体回滚，客户端全部保持 pending 重推 | ✅ 合格 |
| pull 多页拉取中途断 | 已翻页游标已落盘，下次从断点续拉 | ✅ 合格（游标每页持久化） |
| 两设备并发 push 同表 | `MAX+1` 竞态 → **重复 sync_seq → 第三台设备永久丢记录** | ❌ 深度分析 2 |
| 写-写并发（UI×同步线程） | 无 WAL/busy_timeout → `database is locked` 上抛给用户 | ❌ 深度分析 1 |
| 时钟回拨/偏移 | LWW 误判负，静默丢数据，无告警 | ❌ 深度分析 3 |
| 已删除数据被拉回 | 墓碑本身参与同步（`is_deleted` 是全字段覆盖），clean 墓碑会被 `purge_deleted` 物理清理；但**只 pull 不 push 的客户端永不清理**（问题 #7）；另一设备离线期间重新编辑同记录 → LWW 复活（协议固有行为，符合「最后写入获胜」语义，但无任何用户可见痕迹） | ⚠️ 部分缺陷 |
| 服务端 401（令牌错误） | 一律显示「离线可用」，用户无法察觉配置错误 | ❌ 问题 #6 |
| 畸形 push 载荷 | `data["updated_at"]` 缺失 → 未捕获异常 → 整批 500 | ❌ 问题 #5 |
| 待同步队列堆积 | 无上限、无监控；每表每批 500 条会自动多轮消化，实际上不会「满」，但持续失败时无任何堆积量提示 | ⚠️ 建议加 `pending` 计数显示 |
| settings.json 并发写 | 游标保存与设置修改可互相覆盖 | ❌ 问题 #9 |

### 4.3 协议改进建议（按必要性排序）

1. **必须做（不修即丢数据）**：`sync_seq` 原子分配（深度分析 2）+ 时钟偏移修正（深度分析 3）。
2. **应该做（低成本高收益）**：
   - **批次校验和**：push 请求头带 `X-Batch-Count`，服务端核对 `len(changes)`，防止代理/截断造成的半批写入（当前事务兜底已覆盖大部分场景，此项为防御纵深）。
   - **响应去重确认强化**：服务端在 push 响应中回带 `batch_id`（uuid），客户端 `mark_clean` 前核对，防止「响应串包」这类极低概率事故。
   - **check 接口利用**：现有 `GET /api/sync/check` 返回 `latest_updated_at`，客户端可在每次同步前比对本地 `max_updated_at`，实现「无变化跳过 pull」——省流量也减少锁竞争。
3. **不需要做（明确否决）**：
   - **版本向量（Version Vector）**：单用户、3~5 台设备、星型拓扑（所有设备只与服务端交换），服务端本身就是天然的全序仲裁者。一旦深度分析 2 修复使 `sync_seq` 可信，版本向量带来的边际收益为零，复杂度成本巨大。**否决。**
   - **操作日志（op-based CRDT）**：当前是状态同步（全字段覆盖），字段级合并对「待办标题」「日记正文」这类整体编辑字段没有意义，反而引入合并歧义。**否决。**
   - **字段级 LWW**：同上理由，记录级 LWW 对本应用语义已足够。**维持现状。**
4. **可选增强（中期）**：软删除墓碑加 `purge_after` 时间窗（如同步确认后 30 天再物理删除），给「误删恢复」留后路——当前 `purge_deleted` 在 push 成功后立即物理删除，恢复窗口为零。

## 6. 改进后预期收益

### 数据安全性
- 消除两类**静默数据丢失**：并发 push 的序列撞号（深度分析 2）与锁冲突导致的用户保存失败（深度分析 1）——这是本次审查价值最高的两项修复。
- token 从「本地明文 + UI 明文 + 云端明文主键」三处泄露面收敛为「仅传输中（HTTPS 后）可见」，云端库文件泄露不再等于账号失守。
- 时钟偏移从「无声判负」变为「修正 + 超阈值告警」，LWW 语义重新可信。

### 同步可靠性
- 异常矩阵中 4 个 ❌ 项全部清零；401/5xx/断网三类故障用户可区分，排错从「猜」变为「看状态栏 + 日志文件」。
- 空转同步（无变化也全量 pull 游标轮询）被 check 前置比对消除，5 分钟周期的无效流量与锁竞争下降一个量级。

### 性能提升预估
- 笔记长文输入：击键响应从 O(全文字数) 降为 O(1)（防抖后台化），5 万字文档从「明显卡顿」到「无感」。
- 首页/记账页 refresh：全表扫描（随年限线性增长）改为索引聚合（毫秒级、内存恒定）；记账页单次构建的表扫描次数从 ≥9 次降为 2~3 次。
- UI 线程写库因 WAL + synchronous=NORMAL，单次提交耗时预计下降 50% 以上（机械硬盘收益更明显）。

### 维护成本变化
- CRUD 重复收敛后，新增一个同步模块的 UI 成本从「抄 200 行改 30 处」降为「填字段定义 + 调两个助手」；删除/保存逻辑 bug 修复从 4~9 处同步修改降为 1 处。
- logging 落地后，用户端排错从「复现 + 口头描述」变为「发 `D:\Data\Dingfengbo\logs\` 日志」，远程支持成本大幅下降。
- 打包构建去掉联网依赖后可离线复现；版本号自增消灭「同版本 MSI 无法重装」的支持工单。
- 成本侧：引入约 15 张表的一个序列表、一个时钟偏移字段、一套 logging 配置——均为一次性投入，无持续维护负担，符合「单机优先、轻量」定位。
