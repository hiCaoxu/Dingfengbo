但**一个季度量级的功能扩张（+1.5 万行）重新积累了新债**，本轮出现 5 个高优先级问题，全部集中在「新功能与既有基础设施的接缝处」：导入数据不进同步队列、周期记账多端重复生成、备份恢复与同步调度器互相打架、三处阻塞操作登上了 Flet 事件循环。它们不是低级错误，而是典型的「功能跑通了、闭环没画完」——修复成本都不高。

### 本轮最值得肯定的 3 个改进

1. **DPAPI 密钥保护**（`app/config.py:104-156`）：ctypes 直调 `CryptProtectData`，密钥与 Windows 用户绑定，`settings.json` 被复制到别的机器/账户也无法解开，失败时优雅降级 base64——v2 建议的「至少 DPAPI」以零依赖方式完整落地。
2. **备份中心的工程闭环**（`app/db/backup.py`）：`sqlite3` 在线快照（WAL 安全）→ `PRAGMA quick_check` 校验 → 恢复前自动再备份 → 释放连接池 → 删 wal/shm → 原子替换；每日一次自动备份 + 微秒级文件名防撞。恢复是「最后一道保险」，这个流程设计是对的。
3. **同步可观测性补全**（`app/db/repo.py:117-286` + `app/ui/sync_detail.py`）：`SyncIssue`（拒收明细：哪张表/哪条/为什么 + 单条重试/忽略/全部重试）、`SyncConflict`（LWW 本地获胜留痕）、设备清单与最近 30 次同步历史——v3 报告说的「error 明细列表」从 UI 增强建议变成了完整功能。

### 当前最危险的 3 个隐患

1. **JSON 导入的数据永远不会上传服务端**（`app/services/data_io.py:124-129` + `app/db/repo.py:389`）：`apply_remote` 把导入行标为 `sync_status="clean"`，而推送只发 `pending`——模块 docstring 承诺的「导入数据参与多端同步」不成立。**换新机导入 JSON 备份后，这批数据永远不会同步到云端**，用户却以为迁移完成了。
2. **周期记账跨端重复生成**（`app/services/budget.py:238-256`）：`generate_due` 在每次启动时执行，本地靠 `next_date` 推进幂等，但生成的 `Transaction` 没有幂等键——两台设备各自启动各自生成同一笔「每月房租」，同步后**双份入账**，直接影响记账正确性。
3. **备份恢复与同步调度器的竞态**（`app/ui/backup_center.py:110-140`）：恢复只替换 DB 文件，不暂停调度、不重置游标——恢复完成后 5 分钟内的自动 pull 会把服务端（可能比备份新）的数据写回刚恢复的库，**悄悄覆盖用户的恢复操作**，且确认文案警告的方向还是反的。

## 4. 关键问题深度分析

### 深度分析 1（P1）：JSON 导入的数据不会上传 —— 「迁移完成」的假象

**根因分析**

```python
# app/services/data_io.py:124-129
applied = apply_remote(session, parsed, owner_id="local")   # 导行走远端合并语义
...
mark_pending_write()   # 只触发 10 秒后的同步调度
```

`apply_remote` 是为「拉取远端变更」设计的，落库后统一 `sync_status="clean"`（`repo.py:389`）——远端数据本来就在服务端，无需回推。但导入场景的数据**只在本地**：`mark_pending_write()` 只是调度同步，真正的推送筛选条件是 `sync_status == "pending"`（`repo.py:69-78`），导入行全是 `clean`，一条都不会被推出去。

后果链：旧机导出 JSON → 新机导入 → 界面上数据齐全（用户确认「迁移成功」）→ 服务端云端始终没有这批数据 → 新机的下一次全量 pull/换第三台设备时数据缺失。这是**静默的数据孤岛**，比崩溃更危险。

**Before / After**

```python
# After（data_io.py import_json 尾部）：导入的行按来源显式标记
def import_json(...) -> dict:
    ...
    applied = apply_remote(session, parsed, owner_id="local")
    # 导入数据只存在于本地：新增/被远端覆盖的行必须回 pending 才会推送，
    # 否则「导入完成」是假象——云端永远收不到这批数据。
    for change in applied:
        if not change.get("changed"):
            continue          # 本地更新的行保持本地版本，同样需要推送
        model = MODEL_BY_TABLE.get(change["table"])
        record_id = str((change.get("data") or {}).get("id"))
        if model and record_id:
            session.execute(
                sql_update(model)
                .where(model.id == record_id, model.owner_id == "local")
                .values(sync_status="pending")
                .execution_options(synchronize_session=False)
            )
    session.commit()
    ...
```

（`changed=False` 的行是「本地较新、导入被丢弃」——本地版本待推送状态可能已被 LWW 判定覆盖丢失，标记 pending 让它重新上传，与导入语义一致。）

**为什么这样改能解决问题**：`apply_remote` 的 `clean` 语义对 pull 是正确的，问题只在导入复用了它。在导入路径尾部把**实际产生本地变更**的行重置回 `pending`，复用既有的推送管线（10 秒后自动推、失败重试、拒收入 `SyncIssue`），不需要新协议、不需要改 `apply_remote` 本身。一行状态翻转，闭环补全。

### 深度分析 2（P1）：周期记账的跨端重复 —— 需要一个幂等键

**根因分析**

```python
# app/services/budget.py:238-256（节选）
while rule.next_date and rule.next_date <= today:
    ... create(session, Transaction, kind=..., note=f"[周期] {rule.name}", ...)
    rule.next_date = advance(...)      # 本机幂等：推进 next_date
```

单机正确：`next_date` 推进后不会重生成。但 `next_date` 本身是 `RecurringRule` 的字段，经同步传播——两端同时在线时序尚可；**两端先后离线启动**时（例：笔记本周一启动生成 10 月账单，台式机周三启动也生成同一笔），各自 `create` 出**不同 UUID 的两笔交易**，note 相同但无唯一约束。同步后双份入账，月度支出直接翻倍——记账应用里最伤信任的错误类型。

**Before / After**

```python
# After：生成的交易用确定性主键，天然幂等
def generate_due(session, today=None):
    ...
    while rule.next_date and rule.next_date <= today:
        due = rule.next_date
        deterministic_id = str(uuid5(NAMESPACE_URL, f"recur:{rule.id}:{due.isoformat()}"))
        if session.get(Transaction, deterministic_id) is None:
            create(session, Transaction, id=deterministic_id, ...)
        # 即便本机库被部分恢复/回滚，重复调用也只生成一次
        rule.next_date = advance(...)
```

`repo.create` 接受 `**fields`，显式传 `id=` 会覆盖默认 `uuid4`。两端用相同的 `(rule.id, due)` 算出相同的 UUID，第二端 `create` 时 flush 抛主键冲突 → 改用先 `session.get` 再建（如上）。服务端 `apply_remote` 的幂等路径（`_same_version` 等值比对）对两条同 id 同内容的数据天然返回 `changed=False`，**协议层无需任何改动**。

**为什么这样改能解决问题**：幂等键把「生成」从「每次启动都可能发生」变为「每个 (规则, 日期) 全宇宙只可能发生一次」。这正是 Diary 按 (owner, date) 合并、`mark_clean` 按版本确认等既有幂等设计的同一思想：**确定性身份优于随机身份**。顺带修掉了「本机恢复旧备份后 generate_due 重生成」的单机边角情况。

### 深度分析 3（P1）：备份恢复与同步调度器的竞态

**根因分析**

恢复流程（`backup_center.py:110-140`）做对了：校验 → pre-restore 备份 → `engine.dispose()` → 删 wal/shm → 复制 → `init_db()` → `refresh()`。但它对**同步子系统一无所知**：

1. `scheduler.py` 的 5 分钟周期与 60 秒提醒循环继续运行；
2. 同步游标持久在 `settings.json`（指向服务端最新位置）；
3. 恢复完成后的第一次 `_pull` 会把服务端数据按 LWW 写回——**用户恢复旧备份的意图被静默回滚**（若云端更新）；
4. `backup.py:188-194` 的 `engine.dispose()` 若撞上后台 sync 线程正持有 session，只留 debug 日志，可能复制到不一致快照。

**Before / After**

```python
# After：恢复期间暂停自动同步，恢复后由用户决定是否拉取
# app/ui/scheduler.py 增加全局开关
_auto_sync_paused = False

def pause_auto_sync(reason: str) -> None:
    global _auto_sync_paused
    _auto_sync_paused = True
    logger.info("自动同步已暂停：%s", reason)

def resume_auto_sync() -> None: ...

# _on_interval / schedule_sync 入口处：
if _auto_sync_paused: return

# app/ui/backup_center.py do_restore：
pause_auto_sync("数据库恢复中")           # ① 先停调度，等 in-flight 同步结束
time.sleep(1.0)                            #    简单等待当前 sync_once 退出（锁内自然完成）
restore_database(...)
init_db()
resume_auto_sync()
# ② 恢复完成提示改为（方向修正）：
snack(page, "已恢复备份。自动同步已恢复：若云端较新，下次同步会以云端为准；"
            "如需保持本备份状态，请先在设置中关闭同步或检查同步明细。")
```

**为什么这样改能解决问题**：竞态的根源是「两个都能写库的子系统互不知情」。暂停标志是单进程内成本最低的协调机制（项目已用同款模式处理 `_pending_timer` 防抖与 `palette` 防重入）。1 秒等待覆盖 `sync_once` 的 10 秒超时窗口并不严谨，更严谨的做法是给 `SyncClient` 暴露 `wait_idle()`（用现有 `self._lock` 的 `acquire/release` 即可实现）；文案修正则是零成本——现在那段「未同步改动请先同步」的警告恰好把用户推向错误操作。

### 深度分析 4（P1）：两处阻塞调用登上了 Flet 事件循环

**根因分析**

Flet 的 `run_task` 协程与事件回调运行在**同一个 asyncio 事件循环**上——任何同步阻塞调用都会冻结整个 UI（连动画和输入都不响应）。项目自己的纪律是「重活进 `run_thread`，回 UI 用 `run_task`」（`async_utils`、`scheduler.py:59-68` 都是正确示范），但新代码有两处破戒：

```python
# ① app/services/system_integration.py:195-202 —— 托盘「立即同步」
async def _sync(self):
    _show("正在同步…")
    sync_client.sync_once()        # 同步 httpx！断网时 timeout=10s，pull 分页可多次请求
    _show(sync_client.status)

# ② app/ui/pomodoro.py:84-87 —— 番茄钟结束
async def done(...):
    ...
    notify(...)                    # services/notify.py:49-62 subprocess.run(timeout=15)
```

断网点一次托盘「立即同步」= UI 冻结 10 秒以上；番茄钟完成瞬间的 UI 卡顿最长 15 秒。

**Before / After**

```python
# After ①：照抄 scheduler 的正确姿势
async def _sync(self):
    _show("正在同步…")

    def worker() -> None:
        sync_client.sync_once()

        async def apply() -> None:
            _show(sync_client.status)
        self._loop.call_soon_threadsafe(...)   # 或直接复用 page.run_task

    threading.Thread(target=worker, daemon=True).start()

# After ②：通知移出协程
async def done(...):
    ...
    def notify_async() -> None:
        notify(...)
    threading.Thread(target=notify_async, daemon=True).start()
```

**为什么这样改能解决问题**：两处的修复都是「把阻塞体搬进线程」的机械改写，风险极低。值得强调的是**规律本身**：事件循环阻塞是这个项目 UI 层当前唯一还在复发的缺陷模式（v4 已出现 4 例：托盘同步、番茄通知、备份恢复、导出）——建议在 `CONTRIBUTING`/开发约定里写一条「协程与事件回调内禁止出现 httpx/subprocess/文件大 IO，统一走 `run_thread`」，让后续代码在 review 时有据可查。

### 深度分析 5（P2）：`background_section` 缺少过期结果守卫

**根因分析**

```python
# app/ui/async_utils.py:35-55（现状，节选）
def load() -> None:
    data = loader()                     # 线程 A：翻月前的查询，耗时 800ms
    async def apply() -> None:
        holder.content = renderer(data) # 线程 A 的结果，迟于线程 B 到达
        page.update()
    page.run_task(apply)
```

时序：用户点「下个月」→ loader_A 启动（旧月）→ 100ms 后又点「下个月」→ loader_B 启动（新月，更快返回并渲染）→ loader_A 的结果 700ms 后到达，**把旧月渲染盖在新月上**。`command_palette.py:242-257` 已经自带 token 守卫（作者知道这个模式），但没下沉到公共原语——于是 todo/finance/diary/timeline 等所有用 `background_section` 的页面都暴露在这个竞态下，`_state` 已更新为新筛选、界面却显示旧数据，用户点进去操作的是错误视图。

**Before / After**

```python
# After：holder 挂自增 token，apply 时校验
def background_section(page, loader, renderer, placeholder="加载中…") -> ft.Container:
    holder = ft.Container(...)
    token = {"value": 0}

    def load() -> None:
        token["value"] += 1
        mine = token["value"]
        try:
            data = loader()
        except Exception:
            ...（既有错误占位逻辑）
            return

        async def apply() -> None:
            if mine != token["value"]:      # 已有更新的查询在途/已完成，本次结果作废
                return
            ...
```

**为什么这样改能解决问题**：与 notes 预览的 `_preview_generation`、v3 深度分析 1 是同一个模式的公共化：**后发的查询拥有更高的代次，先前的结果一律过期**。单点修改，全部已接入页面（约 10 处）同时受益；`background_section` 的既有调用方签名不变，零迁移成本。

## 5. 专项审查：图片上传与备份（新增攻击面/数据面）

### 5.1 图片上传链路（结论：设计与实现质量高，边界已收）

- **客户端**（`app/services/images.py`）：本地压图（长边 1600 / JPEG q82 / 透明转白底 / 动图原样）→ 压缩后仍 >12MB 拒绝 → 后台线程上传（`uploads.py:54-79`）→ 失败仅 snack、不丢用户输入。错误文案按 401/404/413 分类，面向用户。
- **服务端**（`server/main.py:258-314`）：**文件头 magic bytes 校验**（后缀可伪造，按内容判断）→ 12MB 上限 → 内容摘要命名（同图去重、URL 稳定）→ 临时文件 + `os.replace` 原子落盘 → Bearer 鉴权。路径注入不可能：文件名完全由服务端摘要生成。
- **`/files` 静态服务**：无鉴权能力 URL（摘要 144 bit 不可猜，`server/main.py:58` 注释明确此设计）。单用户部署可接受；遗留两个小项：无 `Cache-Control`（客户端每次全量拉图）、无文件清理策略（P4 清单 #20）。
- **部署注意**：启用 Caddy 反代后必须设置 `DINGFENGBO_SERVER_PUBLIC_URL`，否则上传返回的是 Docker 内网地址（`_public_base` 已预留该环境变量，README 未提——补充进部署文档）。
- **加固建议**（#18）：`await file.read()` 前先查 `Content-Length`，防止超大 body 先进内存。

### 5.2 备份/导出（结论：流程严谨，两个边界）

- 备份本体（`app/db/backup.py`）如总评第 2 点，设计正确。遗留边界：恢复与同步调度的竞态（深度分析 3）、恢复/备份在 UI 线程执行（#4）。
- **导出包含凭证字段**（#16）：`export_full_data` 打包整个 `settings.json`。由于 token 已 DPAPI 加密（跨机解不开、解密失败返回空并告警），**实际泄露面很小**——反而是「换机导入导出包后密钥静默变空」会困惑用户。建议导出时显式剥离 `sync_token`/`ai_api_key` 两个键并提示。
- CSV 导入的两个数据风险（#13）建议在导入对话框文案中至少提示「按 ID 覆盖、不比较时间」。

## 8. 改进后预期收益（v4）

- **数据安全**：消除「迁移假象」（导入不推同步）与「记账翻倍」（周期重复）两个**静默数据错误**——这是本轮价值最高的两项；恢复操作不再被自动同步悄悄回滚，备份作为「最后保险」的承诺真正成立。

- **维护成本**：`background_section` 补 token 守卫与开发约定文档化「事件循环禁阻塞」后，本轮唯一复发的缺陷模式（UI 线程纪律）有了制度 + 原语双重防线；279 个测试为上述所有修复提供了可靠的回归基座（预计修复后新增 10~15 个测试）。
