### 当前最危险的 3 个隐患

1. **`sync_sequences` 计数器未从存量数据初始化**（`server/main.py:108-116` + `app/db/migrations.py:37-47`）。在**已有数据的 cloud.db** 上升级后，全局序列从 1 重新开始，而存量行带着旧的表内序列号（可能已达数百），存量客户端游标 `sync_seq > cursor` 将**永久漏拉新推送**——v1 深度分析 2 的竞态修好了，但引入了同等级别的迁移缺陷（仅影响有历史数据的部署，全新部署无此问题）。
2. **服务端 `rejected` 不回传记录 id**（`server/main.py:188-198`），客户端 `mark_clean` 只认 `accepted`——被永久拒收的记录会永远挂在 pending 队列里，每 5 分钟 + 每次写入后重复推送、重复被拒，形成静默的无效流量循环。
3. **AI 上下文会把日记/收支等私密数据发往第三方大模型，全程无用户确认**（`app/services/ai/context.py:77-96` → `app/ui/ai_assistant.py:198-203`）。`@` 引用机制设计得很克制（30 条上限、剥离同步元数据），但首次使用没有「数据将发送至 xxx」的知情权提示，对个人工作台这类高隐私应用是必须补齐的一环。

## 4. 关键问题深度分析（本轮新发现）

### 深度分析 1（P0）：`sync_sequences` 未从存量数据初始化 —— 升级版部署的增量漏拉

**根因分析**

原子领号实现本身是正确的：

```python
# server/main.py:108-116
session.execute(
    text("INSERT INTO sync_sequences(id, value) VALUES(1, 0) ON CONFLICT(id) DO NOTHING")
)
hi = int(session.execute(
    text("UPDATE sync_sequences SET value = value + :n RETURNING value"), {"n": n}
).scalar_one())
```

问题在**初值 0**。升级前，服务端各行带着旧方案分配的表内序列号（如 `todos` 已到 150）；客户端游标（`settings.json` 里按 `sha256(server+token)` 分键持久化）记录的就是这些旧值。升级后：

1. 新 push 的记录领到全局序列 1、2、3……
2. 存量客户端 pull 条件 `sync_seq > 150`（`server/main.py:162`）——新记录**永远不满足**，静默漏拉，且没有任何报错；
3. 更隐蔽的是 `app/db/migrations.py:37-47` 的 `_assign_missing_sequences` 仍按**表内** MAX+1 给 `sync_seq=0` 的存量行补号，补出的号可能大于全局计数器当前值，进一步打乱「全局单调」假设；`pull` 的 `ORDER BY sync_seq` 在两种编号体系混排时也不再对应真实写入顺序。

`tests/test_server_sync.py:158` 断言 `min(seqs) == 1`，恰好从测试角度证实了计数器从 1 起步——该测试用的是全新内存库，覆盖不到升级场景。

**Before / After**

```python
# Before（app/db/migrations.py:61-64）：只建表，不初始化计数器
if not legacy_tables:
    Base.metadata.create_all(connection)
    _assign_missing_sequences(connection)
    return

# After：建表后把全局计数器锚定到存量最大 sync_seq，
# 并让缺号补偿也从全局计数器领取，保证全局单调
def _assign_missing_sequences(connection: Connection) -> None:
    connection.execute(
        text("INSERT INTO sync_sequences(id, value) VALUES(1, 0) ON CONFLICT(id) DO NOTHING")
    )
    # 1) 计数器锚定到全表最大 sync_seq（升级存量库的关键一步）
    max_seq = 0
    for model in SYNC_MODELS:
        found = connection.scalar(select(func.max(model.sync_seq))) or 0
        max_seq = max(max_seq, found)
    connection.execute(
        text("UPDATE sync_sequences SET value = :v WHERE id = 1 AND value < :v"),
        {"v": max_seq},
    )
    # 2) 缺号行改从全局计数器逐段领取（替代旧的表内 MAX+1）
    for model in SYNC_MODELS:
        ids = connection.scalars(
            select(model.id).where(model.sync_seq == 0).order_by(model.updated_at, model.id)
        ).all()
        if not ids:
            continue
        hi = int(connection.execute(
            text("UPDATE sync_sequences SET value = value + :n RETURNING value"),
            {"n": len(ids)},
        ).scalar_one())
        for offset, record_id in enumerate(ids):
            connection.execute(
                update(model).where(model.id == record_id)
                .values(sync_seq=hi - len(ids) + 1 + offset)
            )
```

同时建议服务端 `server/main.py` 在 `initialize_schema(engine)` 后记录一行启动日志：`logger.info("同步序列当前值：%s", ...)`，部署后肉眼可核对。

**为什么这样改能解决问题**

游标语义的根基是「`sync_seq` 全局单调递增且永不重用」。把计数器锚定到存量最大值后，新分配的号严格大于所有历史号，存量客户端的 `>` 游标条件重新严密；缺号补偿改走同一计数器，杜绝双编号体系并存。该改动对全新部署是无操作（`max_seq = 0`），对升级部署一次性自愈，且全部在 `initialize_schema` 的既有事务内完成，不需要额外迁移脚本。

### 深度分析 2（P1）：`rejected` 无 id —— 永久 pending 的静默重推循环

**根因分析**

```python
# server/main.py:188-198 —— rejected 只有 reason
except ValidationError as exc:
    reason = exc.errors()[0].get("msg", "无效变更") if exc.errors() else "无效变更"
    rejected.append({"reason": str(reason)})
```

客户端只处理 `accepted`：

```python
# app/services/sync.py:115-117
accepted = payload.get("accepted", [])
with session_scope() as session:
    mark_clean(session, accepted)
```

一条通不过 `Change` 校验的记录（例如未来某版本客户端写了新版字段、或本地数据异常导致 `updated_at` 畸形），服务端每批都拒、客户端每轮都推：5 分钟定时 + 写后 10 秒 + 启动，三个触发源无限循环，且两端日志都不含记录 id，排查时连是哪条记录都不知道。虽然当前客户端自身不会产生非法载荷（所以触发概率低），但这是协议层的「只进不出」缺陷，一旦触发永不自愈。

**Before / After**

```python
# Before（server/main.py:194）
rejected.append({"reason": str(reason)})

# After：带上 id 与 table，让客户端能精准定位
record = raw.get("data") or {}
rejected.append({
    "table": raw.get("table"),
    "id": record.get("id"),
    "reason": str(reason),
})
```


```python
# app/db/repo.py 新增：
def mark_rejected(session: Session, rejected: Iterable[dict], owner_id: str = "local") -> None:
    """被拒记录标记为 error 退出待同步队列，避免无限重推；用户重新编辑后由 mark_dirty 复活。"""
    for item in rejected:
        model = MODEL_BY_TABLE.get(item.get("table") or "")
        record_id = item.get("id")
        if model is None or not record_id:
            continue
        session.execute(
            sql_update(model)
            .where(model.id == str(record_id), model.owner_id == owner_id,
                   model.sync_status == "pending")
            .values(sync_status="error")
            .execution_options(synchronize_session=False)
        )
```

（`sync_status` 现有取值 `pending/clean`，新增 `error` 不需要改表结构；`mark_dirty` 会把重新编辑的记录重置回 `pending`，自愈路径天然存在。UI 侧可在设置页显示「N 条记录同步被拒」作为可见性闭环。）

**为什么这样改能解决问题**

协议增加「拒收回执 → 客户端出队」的闭环后，非法记录从「无限重推」变为「推一次、标记、静默退出」，用户再次编辑该记录时 `mark_dirty` 自动复活重推——不需要任何人工干预，也不需要新的同步状态机。

### 深度分析 4（P2）：记账汇总仍是「循环查全表」

**根因分析**

分页已下推 SQL（`finance_ui.py:220-231`），但聚合层仍是 v1 的模式：

```python

    for each of last 6 months:

# app/services/finance.py:78-92 —— month_summary 在 Python 里求和
rows = session.scalars(select(Transaction).where(...月份...))
income = sum(r.amount for r in rows if r.kind == "income")

# app/services/finance.py:51-60 —— account_balances 全表加载
for tx in session.scalars(select(Transaction).where(is_deleted == False)):  # 全部历史
    ...

# app/ui/finance_ui.py:216-219 —— 年份选项全量取日期再 Python 去重
```

记账页一次 `build` ≈ 8 次扫交易表；交易上万条后每次进记账页都有可感知的停顿。

**Before / After**

```python
# After：一条 GROUP BY 出六个月趋势
def six_month_trend(session, owner_id="local") -> list[dict]:
    since = first_day_of_month(today() - 5 months)
    stmt = (
        select(
            func.strftime("%Y-%m", Transaction.date).label("ym"),
            Transaction.kind,
            func.sum(Transaction.amount),
        )
        .where(Transaction.is_deleted.is_(False),
               Transaction.owner_id == owner_id,
               Transaction.date >= since,
               Transaction.kind.in_(("income", "expense")))
        .group_by("ym", Transaction.kind)
    )
    ...  # 透视成 [{month, income, expense}, ...]

# After：账户余额一次 GROUP BY
def account_balances(session, owner_id="local") -> dict:
    stmt = (
        select(Transaction.account_id, Transaction.kind, func.sum(Transaction.amount))
        .where(...)
        .group_by(Transaction.account_id, Transaction.kind)
    )

# After：年份选项
select(func.distinct(func.strftime("%Y", Transaction.date)))
```

**为什么这样改能解决问题**

`strftime('%Y-%m', date)` + `GROUP BY` 是 SQLite 聚合的惯用法，8 次全表扫描收敛为 3 次索引范围聚合，结果集从「全部交易行」变为「月份×2 + 账户数×3」的常数级行数，耗时与数据总量基本脱钩。金额用 `func.sum` 在 SQLite 内完成，也顺带降低了 Python 侧浮点累加的次数（彻底消除分位误差需 decimal 迁移，属中期项，本轮不强推）。

### 5.2 新增风险：时钟偏移方案的二阶效应（提示，非缺陷）

`mark_dirty`（`app/db/repo.py:30`）把 `updated_at` 对齐到服务端时间轴后，需注意两点：

1. **`created_at` 未对齐**（`models.py:33` 用本地 `utcnow`）——不参与 LWW，无正确性问题；但如果未来 UI 要按 `created_at` 排序展示「最近创建」，时钟快/慢的设备上顺序会失真。建议保持现状即可，知晓即可。
2. **离线期间偏移为 0**：长时间离线后首次写入的记录用本地时钟，联网同步后才获得偏移——若本机时钟慢，这批记录的 `updated_at` 在服务端 LWW 中天然吃亏。这是协议固有近似，偏移在一次成功同步后即收敛，可接受；极端场景（离线数周且多端并发编辑同一记录）才可见，不处理。

## 7. 改进后预期收益（v2）

### 数据安全性
- 消除升级版部署的**增量漏拉**（深度分析 1）——这是本轮唯一可能造成生产数据不一致的项，修复后同步协议在「全新部署 / 升级部署 / 多端并发 / 时钟异常」四个象限全部闭合。
- rejected 闭环消除「坏记录无限重推」的长期磨损；AI 数据外发从「默认透明」变为「用户知情」。

### 同步可靠性
- 异常矩阵 12 项全绿（v1 为 4 ❌ 2 ⚠️）；剩余工作全是可观测性（pending/error 计数可见），协议层已无需投入。

### 性能提升预估
- 记账页：8 次全表扫描 → 3 次索引聚合，万条交易下从「可感知停顿」到「无感」。
- 日记/笔记列表：大字段延迟加载后，列表页内存占用与加载时间随正文体积脱钩。

### 维护成本变化
- 文档/脚本/产物三者对齐后，分发相关的心智负担归零；save 骨架收敛后，9 处复制 → 1 处助手，新增模块表单成本进一步下降。
- AI 模块当前的 Provider 抽象 + 配置预设（`AI_PROVIDERS`）结构良好，后续接本地模型（Ollama）只需新增 Provider 实现，无需动 UI——这部分不需要任何改进投入。
