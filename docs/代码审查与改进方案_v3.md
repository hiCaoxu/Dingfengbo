## 4. 关键问题深度分析

### 深度分析 1（P2）：笔记预览防抖的模块级全局竞态

**根因分析**

```python
# app/ui/notes.py:27,32（模块级）
_preview: ft.Container | None = None
_preview_timer: threading.Timer | None = None
```

`build_preview(page, note, on_back)` 每次打开笔记都会把新容器赋给全局 `_preview`；而 `_update_preview` 只在**下一次击键**时取消旧 timer（`notes.py:276-284`）。时序：

1. 用户编辑笔记 A，击键 → 启动 400ms timer（闭包捕获 A 的文本）；
2. 400ms 内点击返回并打开笔记 B → `build_preview` 重绑 `_preview` 为 B 的预览容器，但 A 的 timer 仍在跑；
3. timer 到点 → `_render_preview(A 的文本)` → 写入**当前**全局 `_preview`（B 的容器）→ B 的预览区显示 A 的内容，直到用户再次击键。

**Before / After**

```python
# Before（notes.py:276-284）：只在新击键时取消
def _update_preview(value: str) -> None:
    global _preview_timer
    if _preview_timer is not None:
        _preview_timer.cancel()
    ...

# After：build_preview 入口处先取消遗留 timer + 生成代次号，渲染前校验代次
_preview_generation = 0  # 模块级

def build_preview(page, note, on_back):
    global _preview_generation
    _preview_generation += 1
    generation = _preview_generation
    _cancel_preview_timer()   # 新增的取消助手，切换笔记时立即作废在途渲染
    ...
    def _render_preview(value: str) -> None:
        ...
        async def apply() -> None:
            if generation != _preview_generation:   # 已切换到其他笔记
                return
            ...
```

**为什么这样改能解决问题**：取消 + 代次双重保险——取消处理「timer 尚未触发」的常见路径；代次号处理「timer 已触发、`run_task` 已排队」的窗口（取消不了已入队的协程）。代次号是全局单调计数，`build_preview` 每次自增，任何旧代次的渲染结果到达时都会发现自己已过期并放弃写入。改动约 8 行，不触碰数据层。

### 深度分析 2（P2）：`background_section` 失败时占位槽永远「加载中…」

**根因分析**

```python
# app/ui/async_utils.py:35-40
def load() -> None:
    try:
        data = loader()
    except Exception:
        logger.exception("后台查询失败")
        return          # <-- 占位槽停在「加载中…」，无用户反馈
```

该函数已被 todo/health/entertainment/notes 四个模块的列表页使用。DB 锁超时（15s busy_timeout 打满）、磁盘错误等场景下，用户看到的是一个永不结束的加载态——比报错更糟，因为它不可解释。

**Before / After**

```python
# After：失败时渲染错误占位 + 重试
def load() -> None:
    try:
        data = loader()
    except Exception:
        logger.exception("后台查询失败")

        async def show_error() -> None:
            try:
                holder.content = ft.Column(
                    [
                        ft.Text("加载失败", size=12, color=ACCENT),
                        ft.TextButton("重试", on_click=lambda e: page.run_thread(load)),
                    ],
                    horizontal_alignment=ft.CrossAxisAlignment.CENTER,
                )
                page.update()
            except Exception:
                logger.debug("错误占位渲染失败", exc_info=True)

        try:
            page.run_task(show_error)
        except Exception:
            pass
        return
    ...
```

**为什么这样改能解决问题**：把「静默失败」变成「可见失败 + 自愈入口」。重试按钮直接复跑 `load` 闭包，不需要调用方任何配合；错误占位与加载占位共用同一个 `holder`，页面结构不变。这是对 `background_section` 单点修改、四处模块同时受益的改法。

### 深度分析 3（P3）：测试工具链断裂（环境级，但影响协作）

**根因分析**

本地 `python -m pytest` 因 `pytest_timeout` 插件与已装 pytest 版本不兼容而**在收集阶段直接崩溃**：

```
pytest_timeout.py:97 parser.addini("timeout", TIMEOUT_DESC, type="float")
AssertionError: assert type in (None, "string", "paths", ..., "bool")
```

pytest 8 收紧了 `addini` 的合法类型，旧版 `pytest-timeout`（<2.7）传 `type="float"` 不再被接受。当前测试只能靠 `python -m unittest discover -s tests` 运行——能跑，但未来任何人（或 CI）按惯例输入 `pytest` 都会一头雾水。`requirements.txt` 也没有锁定测试依赖，同样的断裂会随机出现在其他机器上。

**修复**

```powershell
python -m pip uninstall pytest-timeout
python -m pip install "pytest>=8" "pytest-timeout>=2.7"   # 如仍需超时控制
```

并在 `requirements.txt`（或新增 `requirements-dev.txt`）中固定：

```
pytest>=8.0,<9
pytest-timeout>=2.7   # 可选；不需要超时控制则不装
```

**为什么这样改能解决问题**：这是纯环境/依赖问题，代码本身无缺陷（unittest 下 33 个测试全部通过即为证明）。锁定测试依赖版本后，「pytest 一跑就崩」这类假故障不会再消耗排查时间；对单人项目而言，可复现的测试命令本身就是最重要的维护资产。
